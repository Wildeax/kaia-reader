```text
R3-H1 | High | The Rust plugin host permits writes and deletion of KOReader sidecars
Files: rust/kaia-app/src/app/plugins.rs:33, rust/kaia-lua/src/bootstrap.lua:92.
The new app host loads settings.reader.lua without applying the shipped Lua app's document_metadata_folder = "dir" default. There is no docsettings shim. A fresh Rust data folder therefore gives the real KOReader DocSettings module its "doc" default. Redirecting DataStorage alone does not redirect book-folder sidecars.
Scenario: enable plugins in a fresh Rust data folder, open a book with a stock KOReader sidecar, and use Move to archive. That plugin calls DocSettings.updateLocation after the native move. With the default "doc" location, updateLocation writes a destination .sdr and purges the source .sdr. Plugins that call DocSettings:open(...):flush() can also overwrite stock reading state beside a book.
Verified with stock_docsettings_writes_book_sidecar. A LuaHost using the app's paths returned "doc" for the metadata location, wrote juliet.sdr/metadata.epub.lua, and removed that source sidecar when updateLocation moved its metadata. All files were scratch copies. The existing docsettings_sidecar_goes_to_the_data_folder test explicitly sets "dir", so it does not cover a fresh app host.
KOReader references: frontend/docsettings.lua:334 and :483, plugins/movetoarchive.koplugin/main.lua:148. The shipped Kaia default is frontend/kaia/defaults.lua:14. Review 1's D-H7 fixes protect sidecars when that default is active. This new runtime never installs it.
Suggested fix: provide a DocSettings adapter for Rust plugin hosting that reads import sources but routes writes, moves and deletion through Kaia-owned state. At minimum, establish the protected location before loading any plugin and prevent a plugin preference from enabling writes to stock sidecars. Add a fresh-host test with an existing stock sidecar and the actual archive workflow.

R3-H2 | High | Plugin file moves delete library history and collection membership
File: rust/kaia-app/src/plugins/library.rs:29.
transfer passes the destination file to Library::scan, which accepts directory roots and skips files. It then removes the source file and calls remove_book on the source row. remove_book cascades to history, covers and collection membership. The destination never gets indexed in this operation. Copy has the same indexing omission without the deletion.
Scenario: put juliet.epub in collection Keep, read half of it, then move it to an archive folder through a plugin. The file reaches the archive, but its old index row and collection membership disappear. Choosing to open the destination fails because App::open_book requires an indexed path. A later directory scan cannot recover the deleted collection and history rows.
Verified with plugin_move_loses_index_and_collection, which calls the committed Host implementation. The move returned success, the source vanished, the destination existed, both index lookups returned no book, and collection membership stayed absent after a rescan.
KOReader reference: plugins/movetoarchive.koplugin/main.lua:144 updates ReadHistory and ReadCollection to the destination. The Rust adapter instead deletes their native equivalents.
Suggested fix: add a library move operation that preserves the book ID and dependent rows while changing its path. Index copied files through a supported single-file operation or directory scan. Publish a complete copy before removing the source, and return success only after the index reflects the destination.

R3-H3 | High | Calibre can read and overwrite private files inside the default downloads root
Files: rust/kaia-app/src/surfaces/catalogs/worker.rs:216 and :331, rust/kaia-app/src/surfaces/catalogs/store.rs:55, rust/kaia-calibre/src/lib.rs:515.
The app gives Calibre the downloads root, which defaults to /mnt/onboard on Kobo. safe_path rejects parent traversal and symlinks but accepts .kaia/settings.json, .kobo/KoboReader.sqlite and .adds/kaia paths as normal components. GET_BOOK_FILE_SEGMENT does not require a known book. SEND_BOOK does not require a supported book extension, and BookStorage::persist replaces an existing target. The later library-format check runs after the replacement.
Scenario: the user connects to a malicious or compromised Calibre endpoint. It sends opcode 14 with {"lpath":".kaia/settings.json"}, then opcode 8 with {"lpath":".kaia/settings.json","length":2,"metadata":{"lpath":".kaia/settings.json","uuid":"overwrite"}}, followed by {}. The endpoint obtains the old settings bytes and replaces the file. The normal settings file can contain OPDS credentials. No ../ path is needed.
Verified with calibre_reads_and_replaces_nonbook_settings through the real catalog Worker and a local TCP server. The server read a 16-byte scratch settings file and replaced it with {}. The transfer failed at indexing only after the overwrite. This requires an explicit user connection, not an unsolicited inbound connection.
KOReader reference: plugins/calibre.koplugin/wireless.lua:623 and :769 also use server lpaths. Copying that behavior does not protect the Rust app's data and installation directories when they share the configured root.
Suggested fix: constrain Calibre to a dedicated book inbox or enforce exclusions for app, system, plugin and sidecar directories. Validate book formats before reading, acknowledging or replacing a target. Restrict file retrieval to known books, and protect metadata paths independently of the advertised extension list.

R3-H4 | High | Plugin document calls put engine work back on the main loop
Files: rust/kaia-app/src/surfaces/reader/mod.rs:142, rust/kaia-app/src/surfaces/reader/plugins.rs:29 and :130.
plugin_tick constructs Host on the app thread. Host opens a second document there. Its text and xpointer methods call sync_text_layout, which paginates that document synchronously on the same thread. The native reader worker does not cover these calls, and reader_busy does not describe this second document.
Scenario: enable a reader plugin whose onReaderReady handler calls self.ui.document:getXPointer(), then open a long EPUB. The event callback lays out the second document while input and Power dispatch wait. A later native layout change can repeat the work on the next plugin text query.
Verified with plugin_reader_attach_blocks_loop. A generated EPUB containing 40,000 short paragraphs and a plugin that only reads its xpointer produced main-loop iterations of 357.1 and 361.8 ms in two desktop debug runs. This is a measured app-thread stall, not a hardware timing claim. Source reading confirms that document opening also runs on that thread.
The native R2-H8 fix is present and its latency tests pass. This is a separate synchronous path introduced by app plugin hosting.
Suggested fix: obtain plugin document facts from the existing engine worker or prepare them on a worker before calling Lua. Keep Lua callbacks on the app thread, but do not open or paginate a document there. Add plugin-enabled input-latency coverage for the first xpointer query and queries after reflow.

R3-H5 | High | A sync queue save failure does not stop the app from exiting
Files: rust/kaia-app/src/app.rs:208 and :267, rust/kaia-app/src/sync.rs:263.
ProgressSync::finish correctly returns an error and retains pending updates when their durable queue write fails. App::shutdown catches it, clears quitting and returns. App::run has already left its loop and returns its earlier Ok result regardless. The process can then drop the only remaining copy of the pending sync update. Clearing quitting at that point cannot resume the loop.
Scenario: a reader has a pending sync position and exits while the queue path is unwritable or storage is full. Shutdown reports a save failure internally, but the normal run method still returns success. The queued position never reaches disk or the server. The book's own saved position is a separate file and is not lost by this defect.
Verified with run_exits_with_unsaved_sync_after_queue_error. The probe made sync-queue.json a directory, scheduled an update for a future deadline, requested quit and called run. run returned Ok while pending_progress still held the update and no queue file existed. It made no network request.
This is a failure-path gap in the R2-M13 shutdown fix. The successful queue-save path no longer joins the network worker, as intended.
Suggested fix: make shutdown return a result that the run loop must handle before committing to exit. On a recoverable queue error, keep the app and its pending update alive, display the failure, and allow retry. Avoid hiding and releasing the reader before that decision is complete.

R3-M1 | Medium | Plugin font settings confuse KOReader units with engine pixels
File: rust/kaia-app/src/surfaces/reader/plugins.rs:399 and :424.
The plugin host returns TextLayout.font_size directly and writes a plugin's font_size directly back to it. TextLayout stores engine pixels. KOReader plugins use the unscaled configurable.font_size value. On the Libra Colour, the native default of 22 KOReader units becomes 47 pixels, but a plugin writing 22 changes the engine size to 22 pixels.
Scenario: a plugin restores font_size = 22 through doc_settings:saveSetting or a SetFontSize event. The text shrinks to roughly half the native default and the app saves that layout. A plugin reading the setting receives 47 instead of 22 before the change.
Verified with plugin_font_units_and_new_book_flag. A plugin on a fresh juliet.epub read 47, wrote 22 and left layout.font_size = 22 in the book's saved state.
KOReader reference: frontend/apps/reader/modules/readerfont.lua:171 and :206 pass the stored size through Screen:scaleBySize before calling the engine. The native R2-M3 default-font fix already performs that conversion.
Suggested fix: convert between KOReader units and engine pixels at the plugin boundary, in both get_setting and set_setting, including configurable.font_size and SetFontSize. Use the same panel scaling rule as the native settings path and test a 22-unit round trip.

R3-M2 | Medium | Directory defaults never apply because plugins always see an existing book
File: rust/kaia-lua/lua/apps/reader/readerui.lua:17.
The reader proxy hardcodes document.is_new = false. DocSettingTweak:onDocSettingsLoad checks that flag before applying directory defaults. The app sends the event with the proxy document, so even a book with no previous Kaia state skips the configured defaults while the plugin reports Works.
Scenario: enable docsettingtweak, save a directory rule with font_size = 30, and open a previously unread EPUB in that directory. The plugin skips the rule at its first condition. Editing the rule and restarting does not change that flag.
Verified by reading the app event path and plugins/docsettingtweak.koplugin/main.lua:77. plugin_font_units_and_new_book_flag also confirmed that a plugin sees false on a fresh book. The existing bundled test at rust/kaia-lua/tests/bundled.rs:765 supplies a synthetic document with is_new = true, so its passing result does not exercise the app path.
Suggested fix: capture whether the book had saved or imported reading state before opening creates its first state file. Expose that fact through ReaderHost and use it for document.is_new. Test the real app lifecycle with an unread book and a saved directory rule.
```
