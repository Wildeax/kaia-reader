R2-H1 | High | Opening unreadable settings destroys the original without telling the reader
Files: rust/kaia-app/src/services.rs:75, rust/kaia-events/src/settings.rs:85 and :207.
Services ignores Settings::open_status. When neither settings file parses, it gets an empty table, creates sync.device_id and immediately flushes it. A recent damaged settings.json has no automatic backup because flush rotates only files older than 60 seconds.
Scenario: a recently written settings file is damaged but still contains recoverable account and preference values. Merely launching Kaia replaces it with a new device ID. The user sees no recovery warning.
Confirmed by running probe_unreadable_settings_overwritten_at_startup. The original marker disappeared and settings.json.old did not exist. This is an app-settings issue, separate from the fixed newer-version handling for book state.

R2-H2 | High | A second app instance silently overwrites the first instance's settings
Files: rust/kaia-app/src/services.rs:76, rust/kaia-app/src/app.rs:248, rust/kaia-events/src/settings.rs:207.
There is no app settings lease or conflict check. Each instance reads its own table and later replaces the whole file. Unique temporary names avoid a filename collision but do not prevent lost updates.
Scenario: A and B open the same data directory. A saves a font change. B later changes warmth and closes. B writes its old copy of the font preference over A's saved value. B can also restore an old sync.enabled value.
Confirmed by running probe_settings_two_writers_clobber. After B shut down, A's persisted reading.font_size was absent. The book-session lease does not protect settings.json.

R2-M11 | Medium | Wi-Fi scripts still block Power and input dispatch
Files: rust/kaia-app/src/surfaces/settings/quick.rs:140, rust/kaia-app/src/app/power.rs:198, rust/kaia-platform/src/network.rs:120.
The quick toggle calls enable_wifi or disable_wifi synchronously. Suspend preparation also executes Wi-Fi shutdown on the app thread. The platform waits for shell commands to finish.
Scenario: toggle Wi-Fi or press Power with Wi-Fi enabled while the DHCP process is slow to exit. release-ip.sh and disable-wifi.sh each permit a five-second wait. Power cannot cancel preparation while that command is running, despite the separate two-second timer being cancellable.
Confirmed by reading the calls and platform/kobo/release-ip.sh:19, disable-wifi.sh:18 and enable-wifi.sh:199. No hardware command was run. This is a remaining integration stall, separate from review 1's fixed thread::sleep pre-suspend delay.

Fixed. The Wi-Fi scripts, the suspend plans and the resume plan run in order on one worker (`rust/kaia-app/src/app/network.rs`). The worker writes through the platform's sysfs root, so a fake device tree stays fake in tests. The finish step, which runs `sync` and then the suspend write, no longer runs on the app thread. A Power press during that write is queued and runs after the write returns, as KOReader does, because its event loop is blocked in that write. The two-second wait still runs on the app thread, and Power still cancels it. The cover of the book being read is prepared on a worker when the book opens (`rust/kaia-app/src/app/sleep_picture.rs`), and Power draws the prepared picture.

The numbers below time the `app.key(Power)` call in a debug build on the desktop.

- Power while a book opens: 960 to 1007 ms before, 10 to 11 ms after. The screen starts as the label on a blank page, and the cover replaces it when the worker finishes.
- Power on a book with a cover: 957 ms before, when the cover was built on the app thread. 21 to 23 ms after, from the prepared picture.
- Finish step while the suspend write waits for one second: 1010 ms on the app thread before. A throwaway probe ran the old `run_plan` call for that step. 0.6 ms after. Power during the write: 1.0 ms after.

The completion fence before suspend (`wait_idle`) still runs on the app thread, because the backend owns the panel handle. The settings flush at sleep also still runs there, and took 7.7 ms in this build.

The test `large_book_open_keeps_power_responsive` in `rust/kaia-app/tests/review2_latency.rs` requires Power under 100 ms during the open and with the prepared cover. The test `power_is_fast_while_the_suspend_plan_runs` in `rust/kaia-app/src/app/power.rs` runs a Libra Colour fake tree whose `/sys/power/state` is a FIFO, so the suspend write waits for a reader. It requires the finish step and Power under 100 ms.

R2-M13 | Medium | Shutdown moves queued network work back onto the app thread
Files: rust/kaia-app/src/sync.rs:238, rust/kaia-app/src/app.rs:243, rust/kaia-app/src/kobo/mod.rs:113.
finish forces pending pushes, closes the channel and joins the worker. The worker processes queued jobs and can drain up to 200 persisted updates. This has no overall shutdown deadline. Requests have individual timeouts, not a bound for the entire drain.

Confirmed by reading the USB return path, shutdown and worker loop. No slow-server test was run. A durable offline queue should allow shutdown to leave pending work for the next run.

## Data safety and app behavior fixes

The tests below cover the assigned findings. The first nine app regression tests failed before the fixes. Queue drain and shutdown tests also reproduced the loss and wait before their fixes. Statistics, jump sync and dictionary tests failed before those paths were enabled. The retained tests pass with the changes.

| Finding | Regression test | Change |
|---|---|---|
| R2-H1 | `unreadable_settings_keep_original_bytes` | Copy unreadable settings and backups before any write. Show a startup notice. A failed copy stops startup. |
| R2-H2 | `second_app_is_refused_until_first_drops` | Hold an OS advisory lock on `kaia.lock` for the services' lifetime. Refuse another app using the folder. `instance_lock_is_released_after_process_death` also kills a child process and reopens the folder. |
